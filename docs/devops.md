# DevOps and observability

## Environments

| | development | production |
| --- | --- | --- |
| compose env file | `env/dev.env` | `env/prod.env` (secrets come from the shell: `PROD_JWT_SECRET`, `PROD_GRAFANA_PASSWORD`) |
| compose project | `docura-dev` | `docura-prod` |
| app / Prometheus / Grafana | :8080 / :9090 / :3011 | :8081 / :9091 / :3012 |
| `APP_ENV` (labels every metric, trace, log) | `development` | `production` |
| public site (GitHub Pages) | `/Docura/dev/` | `/Docura/` |

```
docker compose --env-file env/dev.env  -p docura-dev  up -d --build
PROD_JWT_SECRET=... PROD_GRAFANA_PASSWORD=... docker compose --env-file env/prod.env -p docura-prod up -d --build
```

The backend keeps its data in memory for now (`STORAGE=memory`); SQL arrives with milestone M4.

## Manual CI/CD promotion

`.github/workflows/ci.yml` runs on every push and pull request (ruff, pytest, typecheck, vitest, build).

`.github/workflows/promote.yml` is **manual only** (`workflow_dispatch`). Actions → *Promote (manual)* → Run workflow →
choose `development` or `production` and a ref. It re-runs the tests, builds the site, and publishes it to the `gh-pages`
branch. The `production` GitHub Environment can require a reviewer, so production needs a second manual approval.

## OpenTelemetry

`backend/app/telemetry.py` sets up traces, metrics and logs and exports them over OTLP/HTTP when
`OTEL_EXPORTER_OTLP_ENDPOINT` is set. The collector (`observability/otel-collector.yaml`) fans out:
metrics → Prometheus, logs → Loki, traces → Tempo. Grafana reads all three.

Application metrics:

| metric | meaning |
| --- | --- |
| `docura_registrations_total` | accounts registered |
| `docura_logins_total{outcome}` | login attempts, `success` or `failure` |
| `docura_companies_created_total` | companies created |
| `docura_rate_limited_total{route}` | auth requests refused by the rate limiter |
| `docura_api_errors_total{code}` | domain errors returned, by code |
| `http_server_duration_milliseconds_*` | request rate and latency per route (FastAPI instrumentation) |

Dashboard: Grafana → *Docura application metrics* (`observability/grafana/dashboards/docura.json`, generated by
`observability/make_dashboard.py`).

## Alerts and the on-call agent

`observability/alerts.yml`: `DocuraLoginFailureSpike`, `DocuraRateLimitHits`, `DocuraApiErrorBurst`,
`DocuraBackendDown`. Alertmanager posts firing alerts to `oncall-agent`, which asks Claude for a triage (likely cause,
first diagnostic steps, roll back or not) and files it as a GitHub issue labelled `incident`. It needs
`ANTHROPIC_API_KEY` and `GH_TOKEN` in the environment; without them it falls back to the rule-based runbook in
`oncall-agent/agent.py` and writes the result to its log.

Try it: send more than five failed logins in a minute and watch the alert fire.

```
for i in $(seq 1 12); do curl -s -o /dev/null -X POST localhost:8080/api/auth/login \
  -H 'content-type: application/json' -d "{\"email\":\"bad$i@example.com\",\"password\":\"wrongpass$i\"}"; done
```
